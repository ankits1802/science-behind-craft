# 0223. The version a removal reached is read by name until the web has moved on, and a page drawn at a version that is gone reads the rest of the current one

A removal still takes what it removed out of the current copy at the next rebuild and drops the
page's kept versions at once, but the copy it reached, the version the web's cached page names, is
kept withheld: read only by a request naming it, never exported, and dropped once the page's
refresh after that rebuild succeeds or twenty minutes after it was replaced. The rest of a page
drawn at a version that is gone is the rest of the current version, and the web's read of the gone
version asks for the page's refresh.

## Context

- **Two decisions met on every release.** Decision 0210 keeps a page's replaced versions so a page
  the web still serves from its cache (revalidate 604,800 s, refreshed on demand after a rebuild)
  reads the rest of the version it names. Decision 0213 drops a page's kept versions in the same
  transaction as any removal, retraction, withdrawal or hiding that changes it, and never keeps the
  copy the removal reached. The post-deploy check publishes and retracts a test fact on Sanganeri
  Hand Block Printing on every release: on 8ac83675 the copy moved from version 94 to 95, version
  94 was not kept, and the web's cached page still named `/crafts/Sanganeri-Hand-Block-Printing/shell/v94-...`
  for about ten minutes, until its refresh landed. Every reader in that window got "The rest of
  this monograph could not be read", and Monograph parity failed on it. Any real removal does the
  same to its pages.
- **The web cannot always move on at once.** A removal's own refresh makes the web read the page
  again, and that read claims the rebuild that takes the removed item out. When another rebuild
  holds the rebuild lock, the claim stands for `REBUILD_RETRY` (10 minutes) before a read can claim
  it again. After the rebuild, `rebuild_wanted` sends the page's refresh (one request, at most 5 s),
  which the web may refuse or never receive, and a browser that loaded the page before the refresh
  asks for its rest only once the reader is idle or scrolls.
- **The rest route could only fail.** `lib/monographRestRead.addressedDocument` read the current
  document when the address named it, else the version it named, else nothing, so a version gone
  was a 404 from the rest route and the slot drew `REST_UNREAD`.
- **A static route cannot refresh its own page.** The craft rest route is rendered statically and
  regenerated by its tags; Next throws when `revalidatePath` or `revalidateTag` is called while it
  renders such a route, and the web holds neither the page refresh's batching nor a place to count
  asks across its function instances. The API holds both (`refresh_pages`, the stored
  copy's row).

## Decision

1. **The copy a removal reached is withheld, not lost.** `drop_kept_versions` is unchanged: it
   drops the kept versions of the pages it changes and marks each one's current copy `removedAt`.
   When a rebuild replaces a marked copy, `_store` keeps it like any other, carrying the mark
   (`StoredDocumentVersion.removedAt`, migration `0120_rest_after_removal`): a withheld version. A
   withheld version is served only to a read that names it (`?version=N` on the craft, family and
   category routes, which the edition and the rest of a page drawn at it read), as `withheld` on the
   served copy (`StoredCopy.withheld`, `ServedDocument.withheld`). The craft export route refuses it
   with `This craft's monograph has no such version.`; the family and category export routes read no
   version. Nothing lists or links it: a page and its Cite this monograph name only the current
   version.
2. **Dropped once the web has moved on, or after a grace.** After a rebuild that moved a page,
   `stored_document_rebuilds.rebuild_wanted` (the rebuild a read claims, the path a removal's
   rebuild takes) sends the page's refresh as before; when the web answers it for every batch, it
   drops the page's withheld versions replaced before the refresh was sent
   (`stored_document_versions.drop_withheld`, under the page's lock). Otherwise the grace ends it: a
   withheld version is not served once `REMOVED_GRACE` (20 minutes, two `REBUILD_RETRY`s) has passed
   since it was replaced (`superseded_row`), the documents step of every sweep (the nightly upkeep, a
   page refresh job, a release) deletes those past it (`drop_expired`), and a later removal of the
   page drops it with the kept versions. Twenty minutes is how long a removal's refresh can take to
   land: the rebuild a read claims runs at once unless another holds the rebuild lock, and then the
   next claim waits one `REBUILD_RETRY`; two retries cover one missed rebuild and the refresh after
   the next, and the release's refresh landed in about ten. It counts from when the version was
   replaced, not from the removal, because the web names a version until its replacement is
   refreshed: a page nobody reads for hours after a removal is rebuilt late, and its withheld version
   still has its twenty minutes. Withholding the copy the removal reached was chosen over keeping
   every kept version of the page until the refresh: the web's page names the current copy, a page
   cached at an older version reads the current rest (item 3), and the older versions leave at once
   as decision 0213 decided.
3. **The rest of a gone version is the current version's rest.** `addressedDocument` reads the
   current document when the address names it, else the version it names, and when that version is
   gone, the current document if it is later than the version the address names, in the address's
   language; nothing otherwise (a current document earlier than the address, or in another
   language). Both rest routes read through it, so the craft shell route and the category rest route
   answer a gone version with the current rest. The page's slot reads its rest through
   `fetchedShellRest` and `fetchedDocumentRest` (`lib/monographRestRead`), which draw a rest of the
   page's version or a later one and never an earlier one, and still show `REST_UNREAD` when the
   route fails.
4. **The read of a gone version asks for the page's refresh.** The craft, family and category
   routes answer the web server's read (`core/rate_limit.is_web_server_read`) of a generated page's
   version below its current copy, neither kept nor withheld within its grace, with the same 404
   and, after it, the page's refresh (`document_reads.refresh_drawn`, `refresh_pages`), claimed at
   most once in `REFRESH_RETRY` (10 minutes) per page (`stored_documents.claim_refresh`,
   `StoredDocument.refreshAskedAt`, migration `0120_rest_after_removal`). A visitor's read, a
   version above the current one and a version still served ask nothing. The 404 carries its
   background work (`document_reads.not_found`), since FastAPI drops a raised error's. The rest
   route's read of the gone version is therefore the ask. Asking from the API was chosen over a
   refresh sent by the web route itself, which cannot send one (Context).
5. **Parity reads it as a reader does.** Nothing in `e2e/parity/parityReady.ts` changes: a page
   drawn at a dropped version is whole once the current rest arrives, so the run passes on a
   release whose post-deploy check retracts its test fact; a rest route that fails for the current
   version still leaves `REST_UNREAD`, and the run names the page with `the rest of the page could
   not be read, so its later chapters are not drawn`.

## Consequences

- **What a reader sees when the head and the rest differ.** A reader holding a page drawn at a
  version that is gone sees its masthead, rail and lead chapter as that version drew them, which
  may still show what the removal took when it stood in the lead chapter; every later chapter, the
  sources list, the quotes a citation mark opens (the kit's data comes with the rest) and Cite this
  monograph are the current version's, so Cite names the current edition, a citation mark in the
  lead chapter whose source the removal took opens no quote, and a source can carry one number in
  the lead chapter and another in the later chapters when the removal changed their order. Nothing
  says so on the page. The next load after the refresh is whole at the current version.
- **What a removal leaves readable.** The version a removal reached answers a read naming it,
  usually until its rebuild's refresh lands seconds after the rebuild, and at most twenty minutes
  after it was replaced; an edition cited before the removal answers 404 once it is dropped and the
  page's tag has expired, and no export ever files it.
- **A gone address keeps the current rest.** The rest route's answer for a gone address is cached
  under that address until the page's tag next expires; the page then names the current version.
- **Tests restated, not loosened.** `backend/tests/db/test_removed_versions_db.py` asserted that
  the copy a removal reached was not kept (`superseded_copy` returning nothing after the rebuild, in
  three tests); each now asserts that copy withheld, with what it removed, until its grace ends and
  gone at its end, as item 1 decides, and two tests are renamed for it.
  `frontend/e2e/monograph-reads-unit.spec.ts` asserted that a rest whose version is gone is not
  found; it now asserts the current version's rest, and keeps the other language and adds an earlier
  current as not found, as item 3 decides. `backend/tests/test_stored_document_rebuilds.py`'s
  harness stands in for the drop and the clock.
- **What is left.** The nightly upkeep, a page refresh job and a release refresh their pages in one
  batch at the end of their run and drop nothing on its answer, so their withheld versions leave at
  the grace. A page whose removal's own refresh never reaches the web keeps its cached page, and what
  the removal took in it, until a later refresh, as before. No entry is added to the debt register.
